## 一、产品概述与本周目标

### 1.1 背景与现状

第六周完成了学情画像、诊断报告和知识漏洞的持久化，第七周进一步增加了个性化复习建议、SRS 到期提醒和学情统计。当前产品已经能够回答：

1. 用户在哪些维度存在知识漏洞；
2. 用户下一步可以复习什么；
3. 哪些知识点已经到达推荐复习时间；
4. 用户过去的总体学习表现如何。

但当前复习链路主要停留在“提醒用户开始复习”，还没有稳定回答以下问题：

1. 用户从知识漏洞入口开始复习后，是否能够自然进入对应知识点的费曼对话；
2. Agent 是否知道用户上次具体在哪个维度、哪个原理上出现问题；
3. 用户重新讲解后，系统如何判断原知识漏洞仍需复习还是已经掌握；
4. 用户能否看见本次复习相较上一次的实际变化；
5. 历史报告、漏洞状态、SRS 时间和学情统计能否保持一致。

因此，第八周不急于横向增加新的大型训练场景，而是优先补齐“诊断—复习—重新讲解—效果验证”的核心闭环。

### 1.2 本周核心目标

1. **第七周功能联调与收口**

   对痛点 Prompt、复习建议、SRS、今日待复习和学情统计进行真实账号端到端联调，修复阻断主流程的数据与交互问题，保证第七周成果能够作为稳定基线使用。

2. **知识漏洞到费曼复习的自然衔接**

   用户从“知识漏洞”或“今日待复习”进入对应知识点时，系统能够保留本次复习所针对的薄弱维度，并进入可识别的复习场景，而不是只更新状态后停留在个人中心。

3. **复习后的漏洞状态联动**

   用户完成重新讲解并生成新报告后，系统根据新结果更新对应知识漏洞。对应维度得分达到 7～10 分的漏洞结束复习，仍为 0～6 分的漏洞继续保留，并避免重复生成相同的未解决漏洞。

4. **复习效果反馈**

   用户能够看见本次复习相较上次诊断的变化，至少明确“哪些问题已经改善、哪些问题仍需继续复习”。具体采用分数变化、状态标签、总结文案或图表，由前后端联调后决定。

5. **真实体验问题优化**

   基于实际联调记录，从 PDF 解析耗时、进度反馈、对话等待、评分稳定性、报告信息层级等问题中选择一个影响最大的体验问题完成可验证优化。本周不预先指定必须优化哪一项，先用数据确定优先级。

### 1.3 本周非目标（暂不纳入 P0）

1. 错题库、错题拍照识别和完整错题复盘场景；
2. 主观题独立训练与标准答案评分系统；
3. 短信、邮件、微信等 SRS 定时推送通知；
4. 数学、政治、计算机、英语等完整学科专属 Prompt 体系；
5. 系统预设教材商城或公共教材资源库；
6. 知识图谱、双模型评分核验和模型微调；
7. 为优化而进行大规模架构重构。

### 1.4 成功指标

| 指标 | 目标值 |
|---|---|
| 第七周 P0 功能真实账号端到端联调通过 | 100% |
| 从知识漏洞/今日待复习进入对应知识点复习成功率 | 100% |
| 重新讲解后对应漏洞状态正确更新 | 100% |
| 同一用户 + 同一知识点 + 同一维度不产生重复未解决漏洞 | 100% |
| 新旧诊断报告均可查询，不因复习覆盖历史记录 | 100% |
| 复习结果反馈与后端数据一致 | 100% |
| 用户数据隔离正确，跨用户数据不可见 | 100% |
| 选定的体验问题具备优化前后对比结果 | 至少 1 项 |
| 后端全量自动化测试和前端生产构建通过 | 100% |

## 三、功能点清单

### 3.1 第七周功能联调与收口（P0）

1. **真实账号链路验证**

   - 用户填写或更新学情画像；
   - 选择真实教材知识点进入费曼对话；
   - 生成包含四维评分和复习建议的诊断报告；
   - 低分维度进入知识漏洞；
   - 开始复习后 SRS 次数和时间正确变化；
   - 今日待复习列表和学情统计正确刷新；
   - 页面刷新和重新登录后数据仍然存在。

2. **评分与数据一致性**

   - 综合分与四维得分之和保持一致；
   - 报告评分基于本轮完整历史讲解，而不是只使用最后一句回答；
   - 报告列表、报告详情、知识漏洞和统计接口使用同一份持久化结果；
   - DeepSeek 返回异常时允许降级，但不得产生结构损坏的报告数据。

3. **SRS 与统计收口**

   - 复习次数递增和下次复习时间计算正确；
   - 到期列表仅返回当前用户的有效复习项；
   - 同一天多次操作不得因为重复点击造成非预期的重复计数；
   - 学情统计的知识点数、对话数、四维平均分和趋势数据与历史报告一致。

> 第七周功能完成合并前，第八周新功能不进入并行开发；可先进行方案评审、Mock 契约和测试用例设计。

### 3.2 后端 A：复习上下文与针对性对话（P0）

1. **识别复习场景**

   当用户从知识漏洞或今日待复习入口进入对话时，后端能够识别本轮属于复习场景，并知道当前复习的知识点及未解决维度。

2. **加载必要上下文**

   复习场景可使用以下信息：

   - 当前知识点及对应教材内容；
   - 用户学情画像；
   - 上一次相关诊断报告；
   - 当前未解决漏洞的维度、得分和原因；
   - 上次报告给出的复习建议。

   上述上下文统一从 `review_attempt`、`diagnostic_report` 和 `knowledge_gap` 读取，不由前端拼装历史诊断内容。

3. **针对性追问策略**

   - 优先验证用户上次没有解释清楚的内容；
   - 不直接向用户泄露完整标准答案；
   - 仍保持费曼学习法的“小白听众式追问”；
   - 当历史上下文缺失时，自动降级为普通知识点对话；
   - 不因加载复习上下文失败而阻断整个聊天流程。

4. **普通场景兼容**

   普通知识点对话、游客模式和没有历史漏洞的用户继续使用现有流程，不要求用户必须先产生知识漏洞。

#### P1 次要功能

1. 根据不同薄弱维度选择不同追问侧重点；
2. 对本轮已经解释清楚的薄弱点减少重复追问；
3. 记录复习模式下的 Prompt 命中策略，便于后续评估。

### 3.3 后端 B：漏洞状态联动与复习效果数据（P0）

1. **漏洞状态自动更新**

   用户完成复习对话并生成新报告后，对同一用户、同一知识点、同一维度的未解决漏洞进行更新：

   - 单维度新得分为 7～10 分：漏洞进入已掌握状态，并退出后续到期提醒；
   - 单维度新得分为 0～6 分：漏洞保持复习中，更新最新评分、原因和复习信息；
   - 本次出现新的低分维度：按照现有规则新增漏洞；
   - 不得为同一个未解决问题重复生成多条漏洞。

2. **历史报告保留**

   每次重新讲解生成新的诊断报告。旧报告作为历史基线保留，不用新报告覆盖旧报告，以支持趋势统计和复习前后比较。

3. **复习结果对比数据**

   后端能够向前端提供本次与上次相关诊断之间的变化信息，至少支持：

   - 对比的知识点；
   - 上次与本次四维评分；
   - 已改善或已掌握的维度；
   - 仍需继续复习的维度；
   - 后续复习状态或建议时间。

   统一通过 `GET /api/v1/reviews/{review_id}` 返回，具体契约见第六章。

4. **幂等与数据一致性**

   - 同一最终报告重复处理时，不重复生成报告和漏洞；
   - 同一次“开始复习”操作不因重复点击累计多次；
   - 报告保存失败或漏洞更新失败时应有明确日志和可恢复策略；
   - 复习结束后，漏洞列表、今日待复习和学情统计的结果保持一致。

#### P1 次要功能

1. 统计每个知识点的复习次数和平均提升幅度；
2. 区分“用户手动标记已掌握”和“系统根据新报告判定已掌握”；
3. 提供最近一次复习结果摘要供个人中心快速展示。

### 3.4 前端：复习入口与效果反馈（P0）

1. **复习入口衔接**

   - “待复习”“复习中”和“今日待复习”中的有效入口可以进入对应知识点；
   - 进入对话后保留知识点信息和本次复习目标；
   - 避免用户点击按钮后只改变状态、却没有进入复习流程；
   - 重复点击时有加载态或按钮禁用反馈。

2. **复习场景提示**

   对话页应让用户知道当前是普通学习还是复习，可提示本次重点，但不直接暴露标准答案。具体文案和布局由前端设计决定。

3. **复习结果反馈**

   新报告生成后展示本次复习结果，至少让用户清楚：

   - 哪些维度有所改善；
   - 哪些漏洞已经掌握；
   - 哪些内容仍需继续复习；
   - 下一步应去哪里或做什么。

4. **页面数据刷新**

   返回个人中心后，漏洞状态、今日待复习数量、历史报告和学情统计应刷新为最新数据，不依赖用户手动刷新整个浏览器。

#### P1 次要功能

1. 复习前后四维分数的小型可视化；
2. 历史报告中增加“首次学习/复习”标识；
3. 复习完成后的轻量动效或阶段性反馈。

### 3.5 真实体验问题优化（P1，候选项择一）

在第七周端到端联调过程中记录实际耗时和失败情况，再由小组选择一个影响最大的方向：

1. **大 PDF 解析体验**：文件大小/页数提示、分阶段进度、解析耗时记录、失败原因和重试反馈；
2. **对话等待体验**：请求等待状态、超时反馈、重复提交保护；
3. **评分稳定性**：同一讲解重复评分的偏差观察、结构校验和异常输出降级；
4. **报告可读性**：信息层级、复习建议长度和行动指引清晰度。

本项验收必须包含优化前后对比，不接受只调整文案或样式但无法说明解决了什么问题。

## 四、完整用户流程

### 4.1 第一次学习与漏洞产生

1. 用户选择教材中的某个知识点进入费曼对话；
2. 用户完成多轮讲解，系统生成新的四维诊断报告；
3. 得分为 0～6 分的维度写入知识漏洞；
4. 报告给出教材重读、关联知识点和优先级建议；
5. 用户在个人中心看到待复习漏洞。

### 4.2 从知识漏洞进入复习

1. 用户打开个人中心的知识漏洞或今日待复习列表；
2. 用户选择某个知识点开始复习；
3. 系统进入对应知识点的对话，并识别本轮复习目标；
4. Agent 结合教材、用户画像和上次薄弱点进行针对性追问；
5. 用户完成本轮重新讲解；
6. 系统生成一份新的诊断报告。

### 4.3 复习结果反馈

1. 系统将新报告与相关历史报告进行比较；
2. 新得分达到 7～10 分的维度更新为已掌握；
3. 新得分仍为 0～6 分的维度继续保留，并更新最新原因和后续安排；
4. 前端展示本次已改善和仍需继续复习的内容；
5. 用户返回个人中心，查看更新后的漏洞、报告、SRS 和学情统计。

### 4.4 异常分支处理

1. **没有历史漏洞**：按普通知识点对话处理，不报错；
2. **历史报告缺失**：保留漏洞信息作为复习上下文，无法对比时不展示虚假变化；
3. **漏洞已被解决**：提示用户状态已更新，可选择普通复习或返回列表；
4. **重复点击开始复习**：同一次操作只生效一次；
5. **复习上下文加载失败**：降级为普通对话，主流程不中断；
6. **LLM 输出异常**：使用结构校验或 Mock 降级，不能写入不完整报告；
7. **游客模式**：可进行普通对话，但不进入需要个人历史数据的复习闭环；
8. **跨用户访问**：返回无权限或资源不存在，不泄露其他用户数据。

## 五、业务规则与数据模型

### 5.1 掌握阈值

本周统一采用单维度 7 分作为掌握边界：

| 单维度得分 | 判定 | 漏洞处理 |
|---:|---|---|
| 0～6 分 | 未掌握 | 创建或保留知识漏洞 |
| 7～10 分 | 已掌握 | 不创建新漏洞；已有未解决漏洞自动转为 `resolved` |

约束：

1. 6 分仍属于未掌握，7 分起才属于已掌握，避免边界重叠；
2. 漏洞按单维度分数判断，不以总分代替；
3. 创建漏洞、继续复习和解决漏洞必须调用同一套阈值常量，禁止在多个 Service 中分别硬编码；
4. 新报告的四维得分仍保持 0～10 分，总分保持 0～40 分。

### 5.2 漏洞状态机

```text
首次报告单维度 0～6 分
        ↓
      open（待复习）
        ↓ 开始复习
   reviewing（复习中）
        ↓ 完成复习并生成报告
  ┌──────────────┴──────────────┐
  │ 新得分 0～6                 │ 新得分 7～10
  ↓                              ↓
reviewing（继续复习）       resolved（已掌握）
  │                              │
  └── 下次复习再次验证      后续报告≤6时重新 open
```

具体规则：

1. 首次诊断为 0～6 分时创建 `open` 漏洞；
2. 用户成功创建复习记录后，目标漏洞从 `open` 变为 `reviewing`；
3. 完成复习且新得分为 7～10 分时，目标漏洞自动变为 `resolved`；
4. 完成复习且新得分为 0～6 分时，目标漏洞保持 `reviewing`；
5. 已解决漏洞在后续普通学习中再次得到 0～6 分时，原漏洞重新变为 `open`，不新增重复记录；
6. 用户仍可手动标记已掌握，记录 `resolution_source=manual`；系统评分自动解决时记录 `resolution_source=assessment`；
7. 手动解决并不永久屏蔽系统诊断，后续新报告为 0～6 分时仍可重新打开；
8. `resolved` 漏洞的 `next_review_at` 必须清空，不再进入今日待复习。

### 5.3 复习次数与 SRS 计算时机

`review_count` 的定义为：该漏洞已经完成并产生有效新报告的复习次数。

因此统一规定：

1. 用户点击“开始复习”时不递增 `review_count`；
2. 仅进入对话、发送一两条消息或中途退出，不计为完成复习；
3. 复习会话成功生成并保存新报告时，当前复习目标中的每个 gap 的 `review_count` 恰好递增 1；
4. 同一最终报告重复提交或接口重试，不得重复递增；
5. `last_reviewed_at` 写入报告成功保存的时间；
6. 如果复习后仍为 0～6 分，按递增后的次数计算 `next_review_at`；
7. 如果复习后达到 7～10 分，`next_review_at=null`；
8. 本轮新发现、但不在本次 `target_gap_ids` 中的低分维度创建为 `open`，`review_count=0`。

SRS 间隔继续沿用第七周规则，但起算时间改为有效复习完成时间：

| 完成后的 review_count | 下次复习间隔 |
|---:|---:|
| 1 | 1 天 |
| 2 | 3 天 |
| 3 | 7 天 |
| 4 | 14 天 |
| 5 及以上 | 30 天 |

示例：

```text
8月12日点击开始复习 → review_count仍为0
8月12日完成对话并生成报告，得分仍为6 → review_count=1
last_reviewed_at=8月12日完成时间
next_review_at=8月13日同一时间
```

### 5.4 新增 review_attempt 表

新增独立复习记录表，用于区分“开始复习”和“完成复习”，并关联新旧报告：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | `review-` 前缀唯一 ID |
| user_id | TEXT | 当前登录用户，建立索引 |
| session_id | TEXT UNIQUE | 本次费曼对话会话 ID |
| kp_id | TEXT | 本次复习知识点 |
| baseline_report_id | TEXT NULL | 开始复习时该 KP 最新一份历史报告 |
| target_gap_ids | TEXT | JSON 数组，保存本轮要验证的 gap ID |
| source | TEXT | `gap` 或 `due`，表示入口来源 |
| status | TEXT | `active` / `completed` |
| result_report_id | TEXT NULL | 完成后生成的新报告 ID |
| started_at | DATETIME | 复习记录创建时间 |
| completed_at | DATETIME NULL | 新报告成功保存时间 |

约束：

1. 一个 `session_id` 只能关联一个 `review_attempt`；
2. 同一用户、同一知识点同一时刻只允许一个 `active` 记录；
3. 用户重复点击开始复习时，后端返回现有 `active` 记录并标记 `resumed=true`，不创建新记录；
4. `target_gap_ids` 只保存属于当前用户、当前 KP 且状态为 `open/reviewing` 的漏洞；
5. `baseline_report_id` 固定为开始复习时的基线，完成后不得改成新报告；
6. 复习中途退出后记录保持 `active`，用户再次点击时继续同一会话；不递增次数，也不丢失原到期信息。

### 5.5 现有表字段调整

`diagnostic_report` 新增：

- `review_attempt_id`：可空；普通学习为 null，复习报告关联对应 review_attempt。

`knowledge_gap` 新增：

- `resolved_at`：可空；进入 `resolved` 时写入；
- `resolution_source`：可空；取值 `assessment` 或 `manual`，重新打开时清空。

原有 `source_session_id` 更新为最近一次影响该漏洞的会话 ID；历史关系以诊断报告和 review_attempt 为准，不依赖该字段保存全部历史。

### 5.6 事务与幂等原则

复习完成时，以下动作必须在同一数据库事务中执行：

1. 新增诊断报告；
2. 更新 review_attempt 为 `completed` 并写入 `result_report_id`；
3. 更新目标漏洞的分数、状态、复习次数和时间；
4. 创建本轮新发现的漏洞。

任一步骤失败时整体回滚，聊天接口可以返回报告内容，但必须记录持久化失败日志，禁止出现“报告已写入但 review_count 重复或漏洞只更新一半”的状态。

## 六、完整接口契约

所有新增接口使用现有 Bearer Token 鉴权。游客调用返回 401；访问其他用户数据统一返回 404，避免泄露资源是否存在。

### 6.1 开始或继续复习

```http
POST /api/v1/reviews/start
Authorization: Bearer {token}
Content-Type: application/json
```

请求：

```json
{
  "kp_id": "kp-dijkstra",
  "source": "due"
}
```

成功响应：

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "review_id": "review-a1b2c3d4",
    "session_id": "session-r1",
    "kp_id": "kp-dijkstra",
    "kp_name": "Dijkstra 算法",
    "baseline_report_id": "rpt-old",
    "status": "active",
    "resumed": false,
    "target_gaps": [
      {
        "gap_id": "gap-depth",
        "dimension": "理解深度",
        "score": 4,
        "gap_description": "未解释贪心选择为什么成立",
        "review_count": 0
      }
    ]
  }
}
```

行为：

1. 查询当前用户、当前 KP 的全部 `open/reviewing` 漏洞；
2. 没有未解决漏洞时返回 409，`msg=no unresolved gaps`；
3. 已有同 KP 的 active 复习记录时返回原记录，`resumed=true`；
4. 否则创建 review_attempt 和新的 session_id，并把 `open` 目标漏洞改为 `reviewing`；
5. 此时不修改 `review_count`、`last_reviewed_at` 和 `next_review_at`。

### 6.2 复习对话

复习引导语扩展现有接口，增加可选 session_id：

```http
GET /api/v1/feynman/greeting?kp_id=kp-dijkstra&session_id=session-r1
```

普通学习不传 session_id，保持现有引导语；复习场景传入 `/reviews/start` 返回的 session_id，后端根据 review_attempt 生成包含复习重点的引导语，但不直接给出标准答案。

对话继续复用现有接口：

```http
POST /api/v1/feynman/chat
```

请求仍为：

```json
{
  "session_id": "session-r1",
  "kp_id": "kp-dijkstra",
  "user_input": "Dijkstra每次会选择当前距离最小的节点……"
}
```

后端根据 `session_id` 查询 active review_attempt，自动加载目标漏洞和基线报告。前端禁止把 `gap_description` 拼进 `user_input` 冒充用户回答。

当对话生成最终报告时，后端自动完成第 5.6 节事务，不增加额外“完成复习”接口。

### 6.3 查询复习结果

```http
GET /api/v1/reviews/{review_id}
Authorization: Bearer {token}
```

复习进行中响应：

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "review_id": "review-a1b2c3d4",
    "status": "active",
    "session_id": "session-r1",
    "kp_id": "kp-dijkstra",
    "kp_name": "Dijkstra 算法",
    "baseline_report_id": "rpt-old",
    "result_report_id": null,
    "dimension_changes": []
  }
}
```

复习完成响应：

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "review_id": "review-a1b2c3d4",
    "status": "completed",
    "session_id": "session-r1",
    "kp_id": "kp-dijkstra",
    "kp_name": "Dijkstra 算法",
    "baseline_report_id": "rpt-old",
    "result_report_id": "rpt-new",
    "dimension_changes": [
      {
        "dimension": "理解深度",
        "previous_score": 4,
        "current_score": 8,
        "delta": 4,
        "result": "mastered",
        "gap_id": "gap-depth",
        "gap_status": "resolved",
        "review_count": 1,
        "next_review_at": null
      },
      {
        "dimension": "表达完整性",
        "previous_score": 6,
        "current_score": 6,
        "delta": 0,
        "result": "continue",
        "gap_id": "gap-expression",
        "gap_status": "reviewing",
        "review_count": 1,
        "next_review_at": "2026-08-13T16:30:00"
      }
    ]
  }
}
```

对比规则：

1. `previous_score` 取 baseline_report 同名维度分数；缺失时为 null；
2. `current_score` 取 result_report 同名维度分数；
3. 两者都存在时 `delta=current_score-previous_score`，否则为 null；
4. `result` 对目标漏洞取 `mastered` 或 `continue`；非目标维度只用于分数展示时取 `unchanged`；
5. 结果由后端计算，前端只负责展示。

### 6.4 今日待复习接口调整

继续使用：

```http
GET /api/v1/gaps/review-due
```

到期项增加以下可选字段：

- `active_review_id`：存在未完成复习时返回对应 review_id；
- `action`：无 active 记录时为 `start`，有 active 记录时为 `continue`。

用户中途退出时，到期项继续保留，但按钮显示“继续复习”，避免 active 记录变成不可恢复的僵尸状态。

### 6.5 手动更新漏洞状态

继续使用：

```http
PATCH /api/v1/gaps/{gap_id}
```

规则调整：

1. `status=resolved` 表示用户手动确认掌握，写入 `resolution_source=manual` 和 `resolved_at`；
2. `status=open` 表示用户主动重新加入待复习，清空解决信息；
3. 前端开始复习不再直接 PATCH `reviewing`，统一调用 `/reviews/start`；
4. PATCH 状态接口不负责增加 `review_count`，也不负责计算 SRS 时间。
5. 直接 PATCH `status=reviewing` 返回 400，避免绕过 review_attempt；
6. gap 正处于 active 复习记录时，手动修改为 open/resolved 返回 409，待本轮完成后再操作。

## 九、验收标准

### 9.1 第七周功能收口

1. 真实登录用户可以完成“对话—报告—漏洞—开始复习—到期查询—学情统计”流程；
2. 旧版“点击开始即递增次数”的逻辑已迁移为“生成并保存有效复习报告后递增”；
3. 今日待复习只展示当前用户已到期的有效记录；
4. 学情统计与历史报告聚合结果一致；
5. 刷新页面和重新登录后数据不丢失；
6. Mock 模式和真实接口模式均可正常运行。

### 9.2 复习上下文与对话

1. 从漏洞入口进入对话后，系统能识别对应知识点和待验证维度；
2. Agent 的至少一个追问能够针对历史薄弱点，而不是完全重复普通问法；
3. 历史上下文缺失时正常降级，不阻断对话；
4. 普通知识点对话行为不受影响；
5. 用户 A 无法读取用户 B 的漏洞与报告上下文。

### 9.3 漏洞状态与报告

1. 复习结束后新增一份诊断报告，原报告仍然可查询；
2. 新得分为 7～10 分的目标维度自动更新为 `resolved`；
3. 新得分为 0～6 分的目标维度保持 `reviewing`，并更新最新结果；
4. 同一未解决漏洞不重复插入；
5. 已掌握漏洞不再出现在今日待复习列表；
6. 点击开始复习不增加次数，完成有效复习后每个目标漏洞只增加 1 次；
7. 同一最终结果重复处理不会生成重复报告、重复次数或重复状态变化；
8. 中途退出后再次点击返回原 active 会话，`resumed=true`。

### 9.4 前端

1. 从知识漏洞和今日待复习入口能够进入对应知识点；
2. 复习场景提示正确，不泄露标准答案；
3. 复习结束后能够看见改善项和待加强项；
4. 返回个人中心后相关列表和统计自动刷新；
5. 重复点击、加载中、空状态和接口错误均有明确反馈；
6. 页面适配桌面 Chrome/Edge，现有主要页面无明显回归。

### 9.5 工程质量

1. 后端增加覆盖状态转换、去重、幂等、用户隔离和异常降级的自动化测试；
2. 前端生产构建通过；
3. 不提交 `.env`、本地数据库、Chroma 向量库、上传 PDF 和构建产物；
4. 新增或变更接口同步更新 Mock 与接口文档；
5. 选定的体验优化项提供优化前后的数据、截图或操作对比。

## 十、非功能需求与风险应对

### 10.1 非功能约束

1. **兼容性**：普通学习、游客模式和存量历史数据继续可用；
2. **鉴权**：涉及历史报告、知识漏洞和复习记录的接口必须登录，按当前用户隔离；
3. **幂等性**：重复请求不能造成重复报告、重复漏洞或复习次数异常增加；
4. **可降级**：复习上下文加载失败时降级为普通对话，LLM 异常时不写入无效结构；
5. **可追踪**：关键状态变化保留必要日志，便于联调定位；
6. **性能**：本周先记录复习上下文加载、LLM 请求和页面加载耗时，不在缺少基线数据时承诺不可靠的固定提升比例。

### 10.2 风险与应对方案

| 风险 | 等级 | 应对策略 |
|---|---|---|
| 第七周 PR 尚未合并，导致第八周基线不稳定 | 高 | 先完成第七周联调、评审和合并，再从最新 `main` 开第八周分支 |
| 阈值常量在多处重复定义导致规则再次分叉 | 高 | 统一使用“0～6 未掌握、7～10 已掌握”的共享常量，不允许各 Service 单独硬编码 |
| 两位后端同时修改核心对话或报告流程产生冲突 | 中 | 先确认上下文与结果契约，再按“对话策略/数据状态”拆分实现 |
| 复习结果过度依赖单次 LLM 评分 | 中 | 本周先保留历史对比和人工可解释信息，不将单次评分扩展为高风险自动决策 |
| 重复点击造成 SRS 次数或状态重复更新 | 中 | 前端加载态 + 后端幂等校验共同处理 |
| 存量历史报告没有 review_attempt 关联 | 中 | 存量报告保持普通报告；新复习以开始时最新同 KP 报告作为 baseline，不强制回填旧数据 |
| 同时加入体验优化导致范围膨胀 | 中 | 体验优化放 P1，只选一个有测量依据的问题 |
| 新功能破坏普通对话流程 | 中 | 将普通对话、复习对话和游客降级纳入回归测试 |

## 附录 A：本周固定实现结论

1. 掌握阈值：0～6 分未掌握，7～10 分已掌握；
2. `review_count` 只在有效复习报告成功保存后递增；
3. 开始复习统一调用 `POST /api/v1/reviews/start`；

7. 复习报告、attempt 和漏洞更新使用同一事务；
8. 系统评分达到 7 分自动解决漏洞，用户手动解决作为可追踪的补充入口；
9. 中途退出不计复习次数，重复开始返回原 active 会话；
10. 前端不再通过 PATCH `reviewing` 启动复习或推进 SRS。
